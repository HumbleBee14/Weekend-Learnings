# Concepts — the four layers, in detail

The level README gave you the headlines. This file is the longer-form version, with the parts that come up in later sub-modules.

## Layer 1 — Dynamo (bytecode → FX graph + guards)

Dynamo is a **partial evaluator** for Python bytecode. CPython compiles your Python function to bytecode once at function-definition time. Normally CPython's `_PyEval_EvalFrameDefault` executes that bytecode. When you `torch.compile` a function, PyTorch installs a frame evaluator (via `PEP 523`, which was specifically lobbied for by the Dynamo team) that intercepts the call.

The intercepted frame is executed **symbolically**: tensors are placeholders, Python ints are tracked as `SymInt`s when possible, and every tensor op is recorded as a node in an **FX graph**. When the interpreter encounters something it cannot symbolically execute, it **graph-breaks**: it stops symbolic execution, returns to normal Python for that statement, then resumes symbolic execution on the other side.

What can graph-break:

- **Direct data access**: `.item()`, `.tolist()`, `.data_ptr()`, `numpy()`, `bool(tensor)`.
- **Data-dependent control flow**: `if tensor.sum() > 0:`, loops where the bound is a tensor.
- **Unsupported builtins or library functions**: arbitrary `print`, `logging.info`, `time.time()`, third-party libraries that touch tensors via C extensions without registering with `torch.library`.
- **Custom Python objects** that aren't pytree-registered.
- **Mutations to non-input tensors** that Dynamo cannot prove safe.

Along with the FX graph, Dynamo emits **guards**. A guard is a Python predicate that must be true for the cached compiled code to be valid. Typical guards:

```
___check_type(L['x'], torch.Tensor)
L['x'].size()[0] == 8
L['x'].size()[1] == 128
L['x'].dtype == torch.bfloat16
L['x'].device == device('cuda:0')
L['x'].stride()[0] == 128
```

Guards are checked on every call. If they pass, the cached code runs (this is cheap — microseconds). If any guard fails, Dynamo re-traces the function with the new input. The cache is keyed by `(function, guards)` and limited to `torch._dynamo.config.cache_size_limit` entries (default 8) per code object. Exceed it and Dynamo permanently falls back to eager for that frame.

## Layer 2 — AOT Autograd (functionalize, joint forward+backward)

Only relevant if you compiled in training mode. Skip this layer for inference.

AOT Autograd takes the FX graph from Dynamo, runs it under a `FunctionalTensor` mode (so in-place mutations become functional copies — `x.add_(y)` becomes `x = x + y`), and traces it again with autograd hooks live. The result is a **joint graph**: forward followed by backward, with the saved-for-backward tensors threaded through.

Then a **partitioner** splits the joint graph back into a forward (returning activations and saved tensors) and a backward (consuming gradients and saved tensors). The default partitioner uses a min-cut heuristic to decide which intermediate tensors to save versus recompute — recomputing some pointwise ops in the backward is often cheaper than holding them in HBM.

This is why training compilation has subtle bugs that inference doesn't: the backward is generated by AOT Autograd, not by you. If something is wrong with the backward, you cannot find the line in your code — you have to read the AOT Autograd output.

## Layer 3 — Inductor (FX → Triton / C++)

Inductor is a scheduler-plus-codegen. It takes an FX graph (either from Dynamo directly for inference, or post-AOT-Autograd for training) and lowers it through a few internal IRs:

1. **Lowering** to `TensorBox` / `StorageBox` IR: each FX node maps to a `loops.Pointwise` or `loops.Reduction` or a template like `mm`.
2. **Scheduling**: groups of operations are fused if their iteration spaces are compatible and the fusion is profitable. Pointwise + pointwise: always. Pointwise + reduction: if the pointwise can be the epilogue of the reduction. Matmul + epilogue: yes, via templates.
3. **Codegen**: each fused group becomes one Triton kernel (on CUDA) or one OpenMP-parallelized C++ function (on CPU). Matmuls go through autotune that benchmarks ATen (cuBLAS), Triton templates, CUTLASS templates, and CuTe-DSL templates (Blackwell only).

The result is written to `~/.cache/torch/inductor/` (or `TORCHINDUCTOR_CACHE_DIR`), and a human-readable `output_code.py` is generated alongside if you set `TORCH_COMPILE_DEBUG=1`.

Things Inductor does well:
- Fuse `RMSNorm + (residual add) + GeLU + dropout` into one kernel.
- Pick a tile size for an elementwise+reduction op.
- Autotune a matmul shape and cache the winner.

Things Inductor does not do well (as of 2.8):
- Cross-kernel scheduling beyond what fusion can express.
- Recognize that two matmuls with the same A operand could share loads.
- Tensor-core MMA pipelining at the level CuTe-DSL or hand-written Triton can do.
- Pick the right algorithm for novel reductions like online softmax (it does softmax fine, but flash attention is too algorithmic).

When you read `output_code.py` you will see the seams of these limitations.

## Layer 4 — The runtime (guard cache, CUDA graphs)

The runtime is the thin layer that ties Dynamo's guards to Inductor's compiled artifacts.

For each compile of a function, the runtime holds:

- The set of guards.
- A reference to the compiled module (a Python `.py` for Triton, a `.so` for C++).
- Optionally, a captured CUDA graph (if `mode="reduce-overhead"` and the compiled code is graph-safe).

On every call, the runtime walks the guard list, picks the first match, and dispatches. CUDA graph capture happens lazily on the first call where shapes match — capture itself is expensive (~10–100 ms), so the first warm call is slow; replays are fast (~1 µs of CPU launch per replay).

CUDA graphs have hard constraints: every tensor address must be the same on every replay. Inductor manages this by maintaining a CUDA graph "pool" of input buffers and copying inputs into them on each call. The cost is one extra memcpy per input; the win is amortizing kernel launch overhead across the whole captured region.

`mode="reduce-overhead"` enables CUDA graph capture for the entire compiled region. **Inductor graph partition** (PyTorch 2.8+) generalizes this: Inductor splits the FX graph at known-unsafe ops (CPU ops, custom ops marked unsafe, `.item()`) and CUDA-graphs each safe partition independently. This is the in-tree version of the piecewise pattern.

The vLLM piecewise pattern goes one step further: it deliberately marks **attention** as a custom op so it becomes a partition boundary, even though attention itself is GPU-safe — the goal is to keep attention out of the graph because attention's shapes change every step (KV cache grows), and re-capturing the whole graph every step would be more expensive than the launch savings.

## How shape specialization works

Dynamo's default policy: every tensor dimension is specialized to the concrete int it saw on first call. The second call with a different size guard-fails and triggers a recompile.

There are three levers to change this:

1. **`torch._dynamo.mark_dynamic(t, dim)`** — tell Dynamo this dim is symbolic from the start. Dynamo emits a `SymInt` for that dim and the FX graph contains symbolic shape expressions.
2. **`torch.compile(..., dynamic=True)`** — make every dim symbolic. Blunt; sometimes worse than the default because of SymInt resolution issues at kernel grid time.
3. **`torch.compile(..., dynamic="auto")`** (PyTorch 2.7+) — start specialized, automatically remark as dynamic after the second recompile. The pragmatic default for production.

`SymInt` is a Python object that represents an integer symbolically. You can add, multiply, and compare SymInts; the result is another SymInt. When a kernel needs a concrete int (a grid size, a Triton constexpr), Dynamo either evaluates the SymInt at runtime or, if the expression is too complex, falls back to a recompile.

## Where each layer lives in the source

- Dynamo: `torch/_dynamo/`. Entry point: `convert_frame.py`. Bytecode rewriting: `bytecode_transformation.py`. Guards: `guards.py`.
- AOT Autograd: `torch/_functorch/aot_autograd.py`.
- Inductor: `torch/_inductor/`. Scheduler: `scheduler.py`. Codegen: `codegen/triton.py`, `codegen/cpp.py`.
- Runtime: `torch/_dynamo/cache_size.py`, `torch/_inductor/cudagraph_trees.py`.

You will not need to read these for this level, but knowing where to grep when you have a specific question is a real skill.
