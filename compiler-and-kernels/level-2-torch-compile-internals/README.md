## 2026 reality check

- **`torch.compile` is the default compile path in vLLM V1.** It's not optional or experimental — it's the primary mechanism. Understanding it is now foundational for anyone working on LLM serving.
- **`depyf`** (`pip install depyf`) is the tool for understanding graph breaks. It decompiles the generated bytecode back to readable Python. It's recommended in the official PyTorch docs now. Use it from day one of debugging.
- **AOTInductor** (`torch._export` + offline compilation) is the path for serving environments that can't have a Python runtime. The compiled artifact is a `.so` file you load with `torch._inductor.aoti_load_package`. vLLM is investing in this for cold-start reduction.
- **Cold-start compile time** is the main pain point. A large model compiles in minutes the first time. Inductor cache serialization (PyTorch 2.6) persists compiled kernels to disk — subsequent starts are fast. The cache key is based on graph structure + hardware + compiler version.

## Architecture: three layers

```
Your PyTorch code
        ↓
  [Dynamo] — bytecode interceptor; builds FX graph; emits guards
        ↓
  [AOTAutograd] — traces forward+backward as a single graph (for training)
        ↓
  [Inductor] — lowers ATen/Prim ops → loop IR → Triton codegen
        ↓
  Triton kernels → PTX → SASS
```

### 01 — `dynamo-bytecode-tracing`

**What Dynamo is.** Dynamo is a Python bytecode interceptor. It hooks into CPython's frame evaluation via `sys.settrace` (and from PyTorch 2.2+, a faster `PEP 523` frame eval hook). When you call a `torch.compile`d function, Dynamo runs your Python bytecode symbolically — instead of computing real values, it builds an FX graph of the PyTorch operations performed.

**Guards.** Every time Dynamo traces a path through your code, it records *guards* — predicates that must hold for the cached compiled graph to be reused. Guards include: tensor shapes, tensor dtypes, Python values used in control flow, and the identity of objects. If a guard fails on a subsequent call, Dynamo retraces.

**Why this matters.** Retracing (guard miss) means you pay the full compile cost again. In serving contexts where input shapes change every request (variable-length prompts), you need to understand which guards are firing and whether you can specialize shapes to avoid misses.

**Inspect guards:**
```python
import torch._dynamo
explanation = torch._dynamo.explain(my_fn)(sample_input)
print(explanation.guard_failures)
```

### 02 — `fx-graph-manipulation`

**The FX graph.** After Dynamo traces, you have a `torch.fx.Graph` — a DAG of `torch.fx.Node` objects, each corresponding to an ATen op. You can inspect, modify, and transform this graph before it reaches Inductor.

**Custom compiler pass.** `torch.compile(backend=your_backend)` lets you intercept the FX graph. A custom backend receives the graph and can: print it, modify it, swap nodes, or lower it to your own hardware target.

```python
def my_backend(gm: torch.fx.GraphModule, example_inputs):
    print(gm.graph)          # print the FX graph
    return gm.forward        # or return a custom compiled callable

model = torch.compile(model, backend=my_backend)
```

**Build steps.** Write a custom backend that: (1) counts the number of matmul ops in the graph, (2) replaces all `torch.ops.aten.mm` with a custom Triton matmul from Level 1. This is the bridge between Level 1 (kernel writing) and Level 2 (compiler integration).

### 03 — `graph-break-diagnosis`

**depyf — the key tool.** `depyf` decompiles the bytecode Dynamo generates back into readable Python source with annotations showing which graph was compiled and where breaks occurred.

```python
import depyf
with depyf.prepare_debug(my_fn, "debug_dir/"):
    with torch.compile(my_fn) as compiled:
        compiled(input)
# debug_dir/ now has annotated Python source with graph break locations
```

**`TORCH_LOGS` environment variables for graph breaks:**
```bash
TORCH_LOGS=graph_breaks python script.py        # log each break reason
TORCH_COMPILE_DEBUG=1 python script.py          # full graph dumps
TORCHDYNAMO_VERBOSE=1 python script.py          # bytecode-level trace
```

**Common graph break patterns and fixes:**

| Break reason | Fix |
|---|---|
| `print()` / `logging` inside forward | Move outside forward, or `@torch.compiler.disable` the logging block |
| Data-dependent tensor shapes (`if x.shape[0] > 10`) | Use `torch.where` instead of Python `if` on tensor values |
| Python list/dict mutation on traced tensors | Use `torch.stack` instead of list append |
| Custom C++ op without meta kernel | Register a meta kernel with `torch.library.register_fake` |
| `torch.no_grad()` context inside forward | Hoist it outside; use `@torch.inference_mode` at the top level |
| Non-traceable Python side effects | Wrap with `torch.compiler.disable()` |

**Build steps.**
1. Take a LLaMA-style block (RMSNorm → attention → MLP). Run `TORCH_LOGS=graph_breaks`.
2. List every break. For each, identify the cause and apply the fix.
3. Re-run. Count how many graphs Dynamo produces — ideally one per inference call.
4. Use `depyf` to visualize the cleaned graph.

### 04 — `inductor-lowering`

**What Inductor does.** Inductor takes the ATen-level FX graph and lowers it to its own IR (`ir.py`), then to a loop-level representation, then to Triton Python code which it JIT-compiles. The generated Triton code is Python — you can read it.

**Read the generated Triton:**
```bash
TORCH_COMPILE_DEBUG=1 python script.py
# Generated kernels appear in /tmp/torchinductor_*/output_code.py
```

Or via `torch._inductor.utils.get_kernel_metadata()` at runtime.

**What to look for:**
- **Pointwise fusion:** multiple elementwise ops (`add`, `mul`, `relu`) fused into one Triton kernel. Look for kernels named `triton_poi_fused_*`.
- **Reduction fusion:** `softmax`, `layernorm` — the reduction + scale in one kernel.
- **Epilogue fusion:** a matmul followed by a bias add fused into the GEMM epilogue (Inductor's CUTLASS backend).
- **Unfused ops:** any ATen op that doesn't have an Inductor lowering falls back to eager. These are the opportunities.

**Build steps.** Run your LLaMA block with `TORCH_COMPILE_DEBUG=1`. Open the generated code. Annotate each kernel: what PyTorch ops does it correspond to? Is it fused or not? Are there any fallback-to-eager ops?

### 05 — `cuda-graph-capture`

**What CUDA graphs do.** CUDA graph capture records a sequence of GPU kernel launches into a single "graph" object. Replaying the graph submits all kernels in one driver call — eliminating per-kernel CPU-GPU synchronization overhead. For LLM decode (many small operations, launch-overhead-bound), this can give 10–30% throughput improvement.

**The incompatibility with dynamic shapes.** CUDA graphs require fixed input shapes. LLM serving has variable sequence lengths. The naive solution (one CUDA graph per shape) is impractical. vLLM's solution: **padding to buckets** — a small set of shape buckets, one CUDA graph per bucket.

**The vLLM piecewise CUDA graph pattern.** vLLM V1 splits the model into:
1. Sub-graph before attention (RMSNorm, Q/K/V projections): static shapes → CUDA graph captured
2. Attention itself: dynamic KV cache access → eager
3. Sub-graph after attention (output projection, MLP): static shapes → CUDA graph captured

```python
# Simplified vLLM piecewise pattern
with torch.cuda.graph() as g_pre:
    output_qkv = pre_attention_block(input)  # captured
    
# attention runs eagerly (dynamic KV length)
attn_output = attention(output_qkv, kv_cache)

with torch.cuda.graph() as g_post:
    output = post_attention_block(attn_output)  # captured
```

**Build steps.** Implement this pattern for your LLaMA block. Measure: throughput with/without piecewise graphs. Observe where the seam between captured and eager produces synchronization points.

### 06 — `aot-inductor`

**What it is.** AOTInductor compiles a model *offline* into a `.so` (shared object) file with no Python dependency. This is the production path for serving environments that want sub-second cold starts and no Python GIL in the inference path.

```python
# Compile offline
import torch
from torch._inductor import aoti_compile_and_package

model = MyModel()
inputs = (torch.randn(1, 512),)
pkg_path = aoti_compile_and_package(torch.export.export(model, inputs), inputs)

# Load in serving (no Python compiler needed)
model_pkg = torch._inductor.aoti_load_package(pkg_path)
output = model_pkg(inputs)
```

**Why vLLM is investing in this.** The multi-minute cold-start compile time when a new vLLM worker starts is a real production pain point. With AOTInductor, the compiled kernels ship as a `.so` artifact alongside the model weights. The worker loads and starts serving in seconds.

**Build steps.** Export your LLaMA block to AOTInductor. Load the `.so` in a separate Python process (simulating a clean worker start). Measure cold-start time vs standard `torch.compile`.

## Common pitfalls

1. **Fixing graph breaks without understanding them.** Wrapping everything in `torch.compiler.disable()` "fixes" the breaks but defeats the purpose. Fix the root cause — the break is usually a real correctness issue.
2. **Assuming Inductor fuses everything.** Inductor fuses pointwise ops greedily but not across reductions or matmuls. Always read the generated output rather than assuming.
3. **Benchmarking without warmup.** The first compiled run includes JIT overhead. Always run at least 5 warmup steps before timing.
4. **Treating the FX graph as implementation-stable.** Inductor's lowering changes between PyTorch versions. Always pin your PyTorch version in production.
5. **Skipping AOTInductor.** Cold-start time is a real production metric. Measure it; don't assume it's acceptable.
